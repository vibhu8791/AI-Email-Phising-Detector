4. Information Collected, Processed & Stored

The application processes only the data strictly required for threat detection:

A. User Identity & Profile Data

  • Google Account Email: Used as your unique tenant identifier.
  • Profile Display Name: Displayed in the top navigation header.
  • Google User ID: Internal alphanumeric ID used to enforce cross-user data isolation.

B. Google OAuth Credentials

  • Access & Refresh Tokens: Received from Google's token endpoint upon successful OAuth consent.
  • Storage & Encryption: Both access and refresh tokens are encrypted at rest using symmetric Fernet encryption (AES-128-CBC with SHA-256 HMAC). Plaintext tokens are never stored in the database and are never sent to browser local storage.

C. Email Message Metadata & Content

  • Header Metadata: Message ID, Subject, Sender address (From), Recipient address (To), and Date/Time timestamp.
  • Message Body Snippets: Plaintext body text and HTML markup extracted to scan embedded URLs, domain reputations, urgency patterns, and suspicious formatting.

D. Forensic Security Artifacts & Risk Scores

  • Extracted URLs: Hyperlinks found within scanned emails, inspected for raw IP addresses, typosquatting, and suspicious top-level domains (.xyz, .top, .buzz, etc.).
  • Machine Learning Probability: A statistical probability score (0.0 to 1.0) generated by our local Scikit-learn TF-IDF vectorizer and Logistic Regression classifier.
  • Heuristic Scores & Flags: Specific detected threat indicators (e.g., “Urgency tactics detected”, “Sender domain mismatch”, “Credential harvesting link”).
  • Composite Risk Score: An aggregated score from 0 to 100 categorizing messages as SAFE (0–39), SUSPICIOUS (40–69), or PHISHING (70–100).

E. Manual Sandbox Submissions

  • Any custom email subjects, senders, and body texts manually submitted into the Sandbox Scanner for on-demand analysis.

F. Session & Authentication Tokens

  • Cryptographically signed JSON Web Tokens (HS256 JWT) stored in browser local storage (phish_auth_token, phish_user_id) to maintain authenticated sessions across page reloads.

5. Storage Location, Retention Schedule & Data Deletion

A. Storage Location

In production, all account credentials (encrypted), email scan records, threat notifications, and forensic analysis results are stored in a persistent MongoDB database hosted in the cloud. In local development mode, a resilient local JSON storage file is utilized.

B. Cross-User Data Isolation

All stored records are partitioned and indexed strictly by the authenticated user_id. Every database query enforces user ownership verification. No user can view, search, modify, or delete another user's email records.

C. Retention Period

Scanned email records and threat logs remain stored in the user's isolated workspace until manually deleted by the user or until account disconnection.

[Configuration Notice • Retention Timeframe]: If you enforce an automated rolling retention window (e.g., automatic deletion of scanned records after 30, 60, or 90 days), specify that exact period here. Currently, data remains until user-initiated deletion.

D. User Data Deletion & Account Disconnection Rights

You have continuous, unilateral control over your stored records:

  • Disconnecting Your Gmail Account: Clicking “Disconnect” in Settings or the Header menu immediately triggers two actions:
    1. The backend sends a token revocation request to Google's OAuth 2.0 revocation endpoint (https://oauth2.googleapis.com/revoke), terminating the authorization with Google; and
    2. Your account record and encrypted access/refresh tokens are permanently erased from our database.
  • Deleting Individual Email Records: You can delete any individual scanned email from the Email History table at any time using the Delete action.
  • Full Data Purge (“Reset Data”): You can instantly purge all scanned email records, metrics, and threat alerts from your workspace by using the Danger Zone > Reset Data action in Settings.
  • Independent Revocation in Google: You may unilaterally revoke the application's access at any time via your Google Account Third-Party Access Portal.

7. Security Controls & Inherent Limitations

A. Technical Safeguards

  • Encryption in Transit: All HTTP traffic, API endpoints, and real-time WebSocket streams (wss://) are enforced over SSL/TLS (HTTPS).
  • Encryption at Rest: OAuth credentials are encrypted at rest with Fernet symmetric cryptography (AES-128-CBC / SHA-256 HMAC).
  • Server-Side Identity Verification: Client-supplied user headers are never trusted. Every protected API endpoint verifies a server-signed JWT Bearer token.
  • CORS Hardening: Production environments enforce strict Cross-Origin Resource Sharing (CORS) origin whitelisting.

B. Limitations & Security Disclaimer

While we implement industry-standard administrative and cryptographic safeguards, no method of transmission over the Internet or electronic storage is 100% secure. The Service operates as an informational security advisory tool; users remain responsible for maintaining general account security (e.g., multi-factor authentication on Google accounts).
